# Backend Planning Doc: Filaments v2
_Generated 2026-11-19_

## Project Context
A private notes repository filled by dictating to Claude in the Claude app. Claude turns speech into a note with a title, Markdown body, and tags, and saves it through a remote MCP server. Claude later finds notes by searching tags and keywords. A web UI for browsing and editing follows in Phase 2.

- **Consumers:** the MCP server (Phase 1) and the Django web UI (Phase 2). Single user.
- **New project**, replacing the Filaments v1 plan (see `PRD.md`).
- **No deadline.** The MVP is voice capture end to end, remote from day one.

## Tech Stack
- **Language:** Python
- **Framework:** Django 5.2 LTS + Django Ninja
- **Database:** PostgreSQL, using Django's ORM and `django.contrib.postgres` full-text search
- **MCP server:** FastMCP 4 (gofastmcp.com), built on the official MCP SDK (pinned `<5`), Streamable HTTP transport, with a stdio entry point for local development only
- **Auth library:** django-oauth-toolkit (OAuth authorization server)
- **Shared schemas:** Pydantic models in a `schemas` package, imported by both the Ninja API and the MCP tools
- **Hosting:** old laptop, Ubuntu Server (headless), Docker Compose (`web`, `db`, `mcp`, `cloudflared`)
- **Exposure:** Cloudflare Tunnel (no open ports on the home network)

## Data Model
### Entities
- **Filament**
  - `id` — UUID primary key
  - `title` — text
  - `body` — Markdown text
  - `source` — `"claude"` or `"web"`
  - `search_vector` — tsvector over title (weight A) and body (weight B), `english` text-search config, with a GIN index. A Postgres generated column (Django `GeneratedField`), so it stays current on every write, including bulk updates. Tags are not part of it
  - `created_at`, `updated_at`
  - `deleted_at` — nullable; set on soft delete
- **Tag**
  - `id` — auto-increment primary key
  - `name` — unique, lowercase, hyphenated

### Relationships
- Filament ↔ Tag: many-to-many (≤8 tags per filament)

### Notes
- **Soft delete:** the default manager excludes rows with `deleted_at` set. A management command hard-deletes filaments soft-deleted more than 30 days ago; a system cron job on the laptop runs it nightly.
- **Tag normalization** happens server-side on every write: trim, strip accents from Latin letters, lowercase, each run of non-letters/digits (spaces, punctuation, `_`) → one hyphen, trim hyphens, dedupe, then get-or-create. Empty or over-long tags are rejected rather than fixed; the 8-tag limit counts tags after dedupe. Implemented in `schemas/tags.py`.
- **No versioning or edit history.**

## API Design
REST with Django Ninja, all routes under `/api/`, no version prefix (single client).

| Method | Route | Purpose |
|--------|-------|---------|
| POST | `/api/filaments` | Create a filament with title, body, tags |
| GET | `/api/filaments` | List newest first; filters: `q` (full-text), `tags` (all must match), `date_from`, `date_to`, `limit`, `offset` |
| GET | `/api/filaments/{id}` | Get one filament |
| PATCH | `/api/filaments/{id}` | Update title, body, and/or tags |
| DELETE | `/api/filaments/{id}` | Soft delete |
| GET | `/api/tags` | All tags with usage counts |
| GET | `/api/health` | Health check (unauthenticated) |

**MCP tools map one-to-one onto these routes:** `create_filament`, `search_filaments` (no query lists newest first), `get_filament`, `update_filament`, `delete_filament`, `list_tags`. Listing and searching were merged into one tool in step 7, since both used `GET /api/filaments`.

- **No real-time** features (no websockets or SSE).
- **OpenAPI docs** are auto-generated by Ninja at `/api/docs` (schema at `/api/openapi.json`), served only when `DJANGO_DEBUG` is on (local development). Ninja doesn't put them behind the service token, so the laptop deployment turns them off.

## Error Handling
- **Shape:** Ninja's default `{"detail": "..."}` with standard HTTP status codes (400, 401, 404, 422, 500).
- **Validation errors (422):** field-level detail, so Claude can see exactly what was wrong with a tool call and retry.
- **Voice-ready responses:** tool results and errors should make sense if Claude reads them aloud in voice mode later: short, plain language, no raw IDs or JSON dumps as the main message.
- **MCP layer:** the MCP server turns API errors into readable tool errors (e.g. "Tag limit is 8; got 10") rather than raw HTTP responses.
- **Unexpected errors:** return a generic 500 message; the full traceback goes to the log only.

## Auth & Authorization
- **Claude → MCP server:** OAuth, with django-oauth-toolkit as the authorization server. The MCP server validates the access token on every request. Signing in during the connector setup uses Ross's Django account.
- **MCP server → API:** a service bearer token (`FILAMENTS_API_TOKEN` in `.env`, at least 32 characters), checked by a small custom Ninja auth class applied to the whole API; only `/api/health` opts out. The MCP server is the token's only holder: the web UI calls the service and query modules in-process. The API listens on the Docker network and localhost only; it is never exposed through the tunnel.
- **Web UI (Phase 2):** Django session login.
- **Roles, permissions, multi-tenancy:** none — single user.
- **Public routes:** `/api/health` and the OAuth endpoints only.

## Business Logic & Edge Cases
- **Most complex piece:** the OAuth flow for Claude's custom connectors.
- **Transactions:** creating or updating a filament and its tags runs in one database transaction.
- **Background jobs:** none, apart from the nightly cron jobs for the soft-delete sweep and backups.
- **External dependencies:** Cloudflare Tunnel only. If the tunnel or the laptop is down, capture fails and Claude reports the tool error.
- **Rate limiting:** none at the app level. OAuth guards the MCP server and Cloudflare sits in front.

## Performance & Scalability
- **Load:** one user, low volume.
- **Caching:** none.
- **Files and uploads:** none in scope (attachments are an open question in the PRD).
- **Search:** Postgres full-text search on `search_vector` (title weighted above body, `english` config), filtered by tags and date range, ordered by rank when `q` is present and by `created_at` otherwise. Keyword search (`q`) also matches tag names, so a note tagged `music` is found by "music" even if its text never says it. `q` is parsed with `websearch_to_tsquery('english', …)`: words are ANDed, and `"quoted phrases"`, `-exclusions` and `or` work. Tag names are appended to the stored vector at query time (weight A), so a query can match words split across tags and text; this skips the GIN index, which is fine at personal scale. Date filters are whole days in the home timezone (`FILAMENTS_TIMEZONE`), and API timestamps are returned in that timezone with their offset. Queries must use the same `english` config as the column.

## Config & Environment
- **Secrets:** a `.env` file on the laptop, read by Django and the MCP server, excluded from Git. A committed `.env.example` lists the required keys.
- **Environments:** local development and the laptop deployment.
- **Feature flags:** none.

## Observability & Quality
- **Logging:** Django's standard logging, written to a file on the laptop.
- **Error tracking:** none (no Sentry).
- **Health check:** `GET /api/health`.
- **Testing:** pytest-django integration tests on the API endpoints and on search (full-text plus tag and date filters), since those are what Claude relies on.
- **Backups:** nightly `pg_dump` to a location off the laptop.
- **Compliance:** none formal; all data stays on owned hardware.

## Deferred Decisions
- Exact OAuth details Claude's custom connectors require (e.g. dynamic client registration, PKCE, token lifetimes)
- How the MCP server validates OAuth tokens: introspection against Django (RFC 7662) or self-contained JWTs it verifies itself. It never reads the token table, because the MCP server does not touch the database
- Backup destination and restore test
- Domain name for the Cloudflare Tunnel hostname
